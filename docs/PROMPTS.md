Джерело: `docs/PLAN.md`. Одне завдання = одна нова сесія Claude Code = одна гілка = один PR.
Самі промпти лежать по фазах у `docs/prompts/phase-N.md` — цей файл лише індекс і правила.

## Як користуватись

### Цикл одного завдання
1. **Нова сесія** в папці `D:\01CLOud CODE\ADHD`. Модель і effort — із заголовка завдання, до першого повідомлення.
2. Вставляєш промпт завдання **цілком**.
3. Агент: ворота → гілка від свіжого `origin/main` → робота → перевірки → блок «Перевірка» → PR.
4. Вердикт `НЕ ГОТОВО` → у тій самій сесії «доробляй обовʼязкові рекомендації».
5. 🔒 → до мержу «↳ Рев'ю» під завданням — у новій сесії; за потреби «↳ Виправлення».
6. Squash-мерж, гілку видалено. Лише тоді — наступне завдання.
7. Кінець фази → «↳ Рев'ю Фази» під `R-N`. Наступна фаза не стартує, доки воно не закрите.

### Автопілот: сесії запускає диспетчер
Замість копіювання руками — одна сесія-диспетчер (Claude desktop, вкладка Code), яка сама стартує сесії кроків **строго по порядку** і мержить. Запускаєш її сам: **Opus 5.5 · effort xhigh** (нова сесія не може мати модель чи effort вище за ту, що її запускає — інакше тихо знижується), вставляєш:

~~~
Ти — диспетчер автопілота РДУГ-бота (D:\01CLOud CODE\ADHD). Код не пишеш і гілок кроків не правиш; читаєш стан, запускаєш сесії, перевіряєш і мержиш.
Дозвіл на мерж даю тут, у чаті: мержиш PR кроку (`gh pr merge --squash --delete-branch`) лише коли (а) CI зелений, (б) блок «Перевірка» = ГОТОВО, (в) для 🔒 — рев'ю з вердиктом ПРИЙНЯТИ або ПРИЙНЯТИ ПІСЛЯ ВИПРАВЛЕНЬ із закритими виправленнями, (г) ти сам звірив твердження «Перевірки» з репозиторієм. Вердикт рев'ю ПЕРЕРОБИТИ — запускаєш «↳ Виправлення». Вибір із рекомендацією всередині сесії — береш рекомендований.
Старт: якщо в папці ще немає git-репозиторію — наступний крок 0.1 (у нього немає воріт і PR: перевіряєш перший коміт у main, приватний репозиторій adhd-bot на GitHub і `bash scripts/check-docs.sh`), далі — за циклом.
Крок циклу:
1. `git fetch`; стан — лише з `origin/main` (`docs/PROGRESS.md`), відкритих PR (`gh pr list`) і файлу рев'ю кроку в `docs/reviews/` на гілці PR.
2. Наступний крок — перший незакритий за порядком `docs/prompts/phase-N.md`: завдання → для 🔒 його «↳ Рев'ю» (коли PR відкритий) → «↳ Виправлення», якщо вердикт не ПРИЙНЯТИ → мерж → наступне завдання; кінець фази — «↳ Рев'ю Фази» `R-N`. Ніколи не перескакуєш, не запускаєш два кроки разом і не відкладаєш крок «на потім».
3. Попередній крок не ✅ на `origin/main` (для 🔒 — PR відкритий, CI зелений) → не запускаєш, пишеш мені чому.
4. Запуск — `start_session`: initiation `user_asked`, context `fresh`, `use_worktree: false` (у папці `node_modules`, `.dev.vars`, кроки йдуть по одному), `model` і `effort` — із заголовка кроку, `prompt` — блок промпту дослівно (перший рядок брифу: «спочатку `cd "D:\01CLOud CODE\ADHD"`»), `background` — «Автопілот: крок такий-то, попередній ✅».
5. Сесія закінчила хід → перевіряєш сам: `gh pr checks`, тести в тимчасовому worktree (`npx vitest run --reporter=dot`), `git ls-files | grep -iE '\.env|\.dev\.vars|secret'`, звірка «Перевірки» з командами. Звіту на слово не віриш → мерж за правилами вище → статус ✅ у `docs/PROGRESS.md` крихітним PR `chore/progress-<крок>` (мерж лише після зеленого CI) → крок 1.
Стоп і питання мені: крок із 👤 (віддаєш мені нумерований список «N — ок / що не так» і потім звіряєш з логом або станом); будь-яка викатка в prod (3.3, 4.3, 5.3, 6.4, 7.3) — мерж так, але `npm run release` лише після мого «викочуй»; вердикт НЕ ГОТОВО двічі; сесія чекає моєї відповіді; страж мержа відмовив; CI червоний; незрозуміло, який крок наступний.
Почни з кроку 1 і скажи, який крок запускаєш.
~~~

Чому диспетчер, а не «кожна сесія запускає наступну»: сесія, яку запустила інша сесія, сама нових сесій не стартує — ланцюжок обірвався б на другому кроці. Після довгої серії кроків без твоїх повідомлень сповіщення чекають — тоді пишеш диспетчеру «далі».

### Чому так
- Свіжа сесія на завдання: контекст чистий, помилки однієї сесії не перетікають.
- `docs/PROGRESS.md` — єдина памʼять між сесіями: статуси, «Борг», «Рішення», нотатка ≤ 5 рядків.
- Ворота в кожному промпті: попереднє не ✅ на `origin/main` → агент зупиняється.
- Огорожа обсягу: «Робиш» / «НЕ робиш»; поза обсягом — зупинись і спитай.
- Таблиці — у своїй фазі; специфікація — зрізами `docs/spec/phase-N.md`: сесія читає свій зріз + `00-common.md`, а не всю спеку.
- Бюджет: файл, який промпт велить прочитати, ≤ 40 КБ; тримає `npm run check:docs` у CI.

### Моделі й effort

| Модель | Коли |
|---|---|
| **Opus 5.5** | специфікації, схема, шар даних, межа з ШІ (prompt injection, медичні дані), черга нагадувань і гонки, викатки, усі рев'ю |
| **Sonnet 5.5** | команди й кнопки за готовою специфікацією, дайджести, налаштування, CI |

| Effort | Коли |
|---|---|
| **medium** | помилку видно одразу в чаті з ботом: команда, кнопка, текст, CI |
| **high** | схема, шар даних, розбір ШІ, ескалація, специфікації, більшість рев'ю; Sonnet-завдання з 🔒 |
| **xhigh** | черга нагадувань (cron двічі, натиск під час повтору), магазин (подвійний натиск «взяти»), перша викатка в prod |

Рев'ю — не нижче за завдання й не нижче high (скрипт робить сам); виправлення — модель і effort автора; двічі не пройшов «Перевірку» по одному критерію → нова сесія на рівень вище.
Викатки 4.3–7.3 — Opus · high, а не xhigh: вони лише запускають скрипт релізу, який 3.3 побудував і рев'ю перевірило на xhigh.

### Гілки
- `main` лише через PR. Завдання: `phase-<N>/<NN>-<коротко>`, документи: `docs/<що>`.
- Кожна гілка від свіжого `origin/main` (`git fetch && git switch -c … origin/main`): після squash-мержу локальний main розходиться з віддаленим.
- Рев'ю пише `docs/reviews/<id>.md` у гілку завдання; рев'ю фази — `review/phase-<N>`, виправлення — `fix/phase-<N>-review`. Якщо гілку кроку вже видалено після мержу — рев'ю читає код у `main` за SHA (`git show <sha>`) у власній гілці `review/<id>`.

### Субагенти
Дозволені для **читання й досліджень** у будь-якому кроці і в рев'ю:
- `Explore` — широкий пошук по коду, коли треба обійти багато файлів; повертає висновок, а не дамп;
- `web-fetch` / `general-purpose` — звірка з живою документацією (grammY, Cloudflare Workers / D1 / Workers AI, Claude API, healthchecks): версії, ліміти, сигнатури — результат у розділ «Рішення» PROGRESS.md з посиланням.

Заборонені:
- субагент, що **пише чи править файли** в реалізації — два «письменники» в одних файлах, і огорожа «НЕ робиш» перестає щось тримати;
- субагент як **рев'ю власного кроку** замість 🔒-рев'ю — та сама сесія не бачить своїх сліпих плям; незалежне рев'ю — лише окремою сесією;
- субагент, що **запускає наступний крок** — порядок тримає диспетчер.

Не більше 3 субагентів на завдання; кожен — із конкретним питанням і форматом відповіді.
