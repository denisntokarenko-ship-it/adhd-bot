## Важливе

**В1. Збій `deployments status` на не-першій викатці мовчки дає `rollback.txt` «перша викатка → deleteWebhook».**
`scripts/release.sh:84` — код виходу `wrangler deployments status` не перевіряється; `:95` вирішує «перша викатка» лише за порожнім `PREV_VERSION`, не за `--first`.
Сценарій (відтворено підмінним `npx`, що на `deployments status` друкує `✘ [ERROR] A request to the Cloudflare API failed` і `exit 1`; без `--first`): «версія до релізу: немає (перша викатка)», реліз іде до кінця з `exit 0`, у `rollback.txt` замість `wrangler rollback <версія>` — коментар «бот замовкає через deleteWebhook». Реліз зламався → людина за `rollback.txt` глушить бота замість повернути старий код (тиша — головний ризик продукту).
Виправити: `FIRST=0` і порожній `PREV_VERSION` → `fail`; рядок про `deleteWebhook` — лише за `FIRST=1`.

**В2. Розбір `migrations list` пропускає міграції, якщо не впізнав імені: «заголовок є, імен 0» → «нових міграцій немає».**
`scripts/release-lib.mjs:50-51` — при наявному «Migrations to be applied» повертає результат `matchAll` як є, навіть порожній; власний контракт функції (`:47` «інше → null (не вгадуємо)») порушено. `release.sh:124` тоді пропускає `apply`, а перевірка після apply (`:127`) ходить тим самим парсером і нічого не ловить.
Сценарій (перевірено `node`): `parsePendingMigrations("Migrations to be applied:\n│ 0006_digests.v2.sql │\n")` → `[]` → «нових міграцій немає» → `apply` пропущено → деплой коду, що чекає `0006`, на стару схему. Те саме — якщо wrangler змінить формат таблиці.
Виправити: заголовок є, а збігів 0 → `null` (стоп); тест з іменем поза шаблоном.

**В3. Перевірка «preview не зачеплено» (3.10.a) не може почервоніти.**
`scripts/release.sh:150` — «до» читається вже **після** `wrangler deploy` (`:135`), «після» — через 2 хв (`:160`). Обидва значення — після prod-деплою, тож якщо деплой зачепив preview, обидва покажуть новий sha і скрипт напише «✓ preview не зачеплено». RUNBOOK §4 п. 1 бере цей рядок за доказ 3.10.a.
Виправити: `PREVIEW_SHA` — до кроку 7 (міграції) або хоча б до кроку 8.

**В4. Справжній шлях релізу (не dry, HEAD = origin/main, D1 створено, кроки 4–10) не тримає жоден тест.**
`test/node/release.test.ts:246-299` — e2e покриває лише «гілка без `--dry-run`» і «dry-run без D1» (обидва виходять до кроку 4). Чисті функції `release-lib.mjs` покриті добре (19/19 мутантів автора — перепрогнано, підтверджено), але bash-обв'язка стопів — ні. Мутанти рев'юера через `scripts/mutate.py` (після коміту, дерево чисте до й після):

| id | що ламає (`scripts/release.sh`) | результат |
|---|---|---|
| R1 | `:128` `[ -z "$LEFT" ] \|\| fail …` → `true` — деплой після часткової міграції | SURVIVED |
| R2 | `:158` `[ -z "$PROBLEMS" ] \|\| fail …` → `true` — червоний `/health` = «ok» | SURVIVED |
| R3 | `:88` bookmark `\|\| fail` → `\|\| true` — міграції без точки відкату БД | SURVIVED |

Сам код зараз правильний (прогнав справжній шлях у копії з підмінними `git`/`npx`/`curl`/`sleep`: «так» → усі 10 кроків і правильний `rollback.txt`; «ні» → стоп до apply, 0 викликів apply/deploy; `/health` зі `stale:true` → 4 спроби → стоп). Але регресію будь-якого з цих чотирьох стопів не помітить ніхто — урок 3.3 «bash-обв'язку — e2e з підмінними git/npm/npx» застосовано лише до гілки.
Виправити: e2e на справжньому шляху (git-заглушка з HEAD = origin/main; шлях до `wrangler.toml` через змінну середовища або копія з справжнім id) і R1–R4 у `docs/mutants/3.3.toml`.

## Дрібниці

**Д1. Стоп після вдалого `wrangler deploy` не каже, що код уже живий.** `release.sh:135-136` — `ok` для деплою ставиться лише після розбору виводу. Деплой пройшов, а в виводі немає `schedule:` (тригер не прив'язався) → «СТОП … деплой без адреси або без cron», у «Зроблено до зупинки» деплою немає → людина може вирішити, що код не викочено, і не відкотити. Виправити: `DONE+=("деплой виконано, версія може бути живою")` до розбору.

**Д2. Перша викатка без `--first` — відкат на порожню заглушку.** `release.sh:95` — `secret put` (RUNBOOK §2) уже створив Worker-заглушку, тож `deployments status` повертає її версію → `rollback.txt` = `wrangler rollback <заглушка>`, команда `setWebhook` наприкінці не друкується (`:174`). RUNBOOK §3 каже `--first`, але скрипт забуте не ловить. Виправити: визначати першу викатку автоматично (наприклад, `/health` prod до деплою не JSON) або відмовляти без `--first`, якщо `/health` prod не відповідає.

**Д3. Поступова викатка: ціль відкату — можливо, нова версія.** `release-lib.mjs:66` — без версії на 100 % береться `versions[0]`. `{versions:[{version_id:"new-50",percentage:50},{version_id:"old-50",percentage:50}]}` → `new-50` (перевірено `node`). Виправити: немає 100 % → `null` і стоп.

**Д4. `API_ROOT` не скидається.** `release.sh:22` скидає `BOT_TOKEN`/`WEBHOOK_SECRET`, але `set-commands.mjs:54` бере хост Telegram із `API_ROOT`. Залишок `API_ROOT=http://localhost:…` в оболонці → prod-токен іде POST-ом на той хост. Імовірність мала (у репо `API_ROOT` ніде не виставляється), виправлення — одне слово в `unset`.

**Д5. Q5 `workers_dev = true` — технічно правильне, але без `preview_urls = false`.** `wrangler.toml:34`. Wrangler 4.165 шле `previews_enabled: undefined` (`node_modules/wrangler/wrangler-dist/cli.js:56616-56625`), і його ж попередження (`:56634`) каже, що Preview URLs за замовчуванням ідуть за workers.dev. Тобто кожна версія prod може мати ще одну публічну адресу `<версія>-adhd-bot-prod.…` з prod-біндингами (D1, секрети). Вебхук там так само під `WEBHOOK_SECRET` (`src/app.ts:31`), тож це не дірка, а зайва поверхня. Виправити: `preview_urls = false` у `[env.production]` (і тест поруч із «S3.10 п. 3»). Саме рішення «workers.dev, а не свій домен» — продуктове, за Денисом; технічно воно потрібне (без адреси вебхуку нікуди вказати, S3.10 п. 3), і інших змін конфігу не тягне.

### 4. Безпека й дані

- **Секрети в логах:** `release.sh` без `set -x`; токен prod-бота — `read -r -s` у змінну, у `set-commands.mjs` — через env дочірнього процесу, `unset` після; у прогоні з токеном-міткою мітка не знайшлась у жодному журналі (`~/adhd-releases/…` у копії) і в журналі викликів. `secret list` → лише назви; `deployments status` (там пошта автора) — лише у файл поза репо, назовні — `version_id`. `curl` ходить лише на `/health` (без токена). Помилки `set-commands.mjs` друкують `description` Telegram, не URL.
- **RUNBOOK:** токен — `Read-Host -MaskInput` у змінну, у URL `api.telegram.org/bot$t/…` підставляється змінна, тож історія pwsh зберігає `$t`, а не значення; `WEBHOOK_SECRET` — з CSPRNG у `$s`, через stdin у `secret put`. Хвостовий перенос рядка з pwsh-пайпа не ламає збіг секретів: wrangler робить `trimTrailingWhitespace(await readFromStdin())` (`cli.js:88083`).
- **Публічний репо:** у `docs/releases.md` і рядку релізу — дата, короткий sha, імена міграцій, bookmark (без доступу до акаунта не дає нічого); `tg_id` у запитах §4 лише вводиться, у виводі — `COUNT(*)`.
- **Шар даних, IDOR, довіра клієнту:** `src/` не змінено — не застосовно. Вебхук prod захищений тим самим `X-Telegram-Bot-Api-Secret-Token` (`src/app.ts:31`).
- Ризики секретів, що лишились: Д4 (`API_ROOT`), Д5 (зайва публічна адреса).
