# Фаза 4 — Ліки й рутини

Читається разом з `00-common.md` (НФ-1, НФ-2, НФ-3, НФ-4, НФ-7). Черга, ескалація, оренда, тиша й анти-шум — `phase-2.md` (S2.2–S2.6, S2.9), огляди — `phase-3.md` (S3.1, S3.2, S3.5): тут лише те, що Фаза 4 до них додає.

## Задача

Ліки й звички — інше, ніж справи: вони повторюються за розкладом, а пропуск ліків має ціну. Людина з РДУГ забуває саме те, що «завжди о 8». Фаза 4 додає **рутини**: майстер кнопками (назва, час, дні), нагадування за розкладом, яке для ліків повторюється до відповіді, і відповідь однією кнопкою — «прийняв ✅», «пропущу», «+15 хв».

Два ризики. **Медичні дані:** назва ліків і факт прийому не потрапляють ні в Claude, ні у Whisper — ні напряму, ні через запасну нотатку, ні через повтор розбору. **Сором:** нагадування про ліки, яке відчувається як контроль, людина замутить разом з ботом. Тому: без докорів, без лічильника пропусків, «пропущу» — нормальна відповідь, вечір рахує лише прийняте.

Кроки: **4.1** схема `0006` і шар даних (S4.1, функції `src/db/` для S4.4–S4.6) · **4.2** майстер, нагадування, кнопки, огляди (S4.2–S4.9) · **4.3** викатка.

## Принципи

1. **Рутина — лише кнопками й одним текстом-назвою.** Жодного виклику Claude чи Whisper у шляху рутини. Назва — єдиний текст, і її бере не розбір, а майстер (S4.3).
2. **Нагадування рутини — рядок тієї ж черги `reminders`.** Оренда, повтори 5→15→30, 403/429, `/health` — без окремого механізму. Відмінності — лише названі тут (тиша, анти-шум, TTL).
3. **Слот** — одна запланована мить прийому: `(routine_id, scheduled_for)`. Відповідь на слот одна назавжди (`UNIQUE` у БД), а не перевірка в коді.
4. **Пропуск не карається, не називається й не перелічується окремо.** `missed` — службовий стан журналу: ні слова «пропущено», ні окремого числа пропусків; він лише входить у знаменник M вечірнього «N з M» (4.9.a).
5. **Огляди без ШІ можуть читати рутини; усе, що йде в ШІ, — ні.** Уточнює принцип 3 `phase-3.md` (див. «Рішення», Р4.6).

## Константи

| Назва | Значення | Що означає |
|---|---|---|

| `TIMES_MAX` | 6 | часів на рутину |

| `ROUTINE_TTL_MS` | 3 год | рядок рутини, що не пішов за 3 год після свого `fire_at` (пауза, збій cron), мовчки `cancelled`; від `fire_at`, не `slot_at` — інакше «+15 хв» через 3 год губило б слот |
| `MISSED_AFTER_MS` | 30 хв | після останньої відправки вичерпаного ланцюга без відповіді — `missed` |
| `ROUTINE_SNOOZE_MIN` | 15 | кнопка «+15 хв» |

| `LATE_MS` | 5 хв, з `phase-2.md` (`src/reminders/plan.ts`) | допуск слота, що вже настав: корінь створюється, поки `slot_at ≥ now − LATE_MS` (S4.4) |
| ескалація | `REPEAT_DELAYS_MIN`, `MAX_ATTEMPTS_ESCALATING` з `phase-2.md` | `med` — 4 спроби, `habit` — 1 |

`days_mask`: біт 0 = понеділок … біт 6 = неділя (ISO 1..7 → `1 << (dow − 1)`), день тижня — локальний у `users.tz` (НФ-1). Час слота — `localToUtc(дата + HH:MM, tz)`.

## Схема (міграція `0006_routines.sql`, крок 4.1)

**`routines`** — ліки чи звичка:

| Колонка | Тип і обмеження |
|---|---|
| `id` | INTEGER PK AUTOINCREMENT |
| `user_id` | NOT NULL → `users(id)` |
| `kind` | CHECK `med, habit` |
| `title` | TEXT NOT NULL, CHECK `length(title) BETWEEN 1 AND 64` і без `char(10)` |
| `times` | TEXT NOT NULL — JSON-масив `"HH:MM"`, відсортований, без повторів; CHECK `json_valid(times) AND json_array_length(times) BETWEEN 1 AND 6` (формат кожного елемента — код) |
| `days_mask` | INTEGER NOT NULL CHECK `BETWEEN 1 AND 127` |
| `escalate` | INTEGER NOT NULL CHECK `IN (0,1)`; майстер ставить 1 для `med`, 0 для `habit` |
| `active` | INTEGER NOT NULL DEFAULT 1 CHECK `IN (0,1)` — 0 = на паузі |
| `created_at`, `updated_at` | INTEGER NOT NULL |

**`routine_logs`** — відповідь на слот:

| Колонка | Тип і обмеження |
|---|---|
| `id` | INTEGER PK AUTOINCREMENT (на нього посилається `points_ledger`) |
| `user_id` | NOT NULL → `users(id)` (НФ-3: кожен запит із `WHERE user_id`) |
| `routine_id` | NOT NULL → `routines(id)` |
| `scheduled_for` | INTEGER NOT NULL — `slot_at` слота (UTC ms) |
| `status` | CHECK `taken, skipped, missed` |
| `answered_at` | INTEGER; CHECK `(status = 'missed') = (answered_at IS NULL)` |
| `created_at` | INTEGER NOT NULL |

`UNIQUE(routine_id, scheduled_for)`; індекс `ix_rlog_user_day (user_id, scheduled_for)`.

**`reminders` — перебудова таблиці** (SQLite не змінює CHECK без неї; CHECK `0004` вимагає `item_id` для всього, крім `digest_*`/`timer`). Нова таблиця = стара + :
- `routine_id` → `routines(id)`, `slot_at` INTEGER; CHECK `(routine_id IS NULL) = (slot_at IS NULL)`; CHECK `item_id IS NULL OR routine_id IS NULL`.
- `kind` CHECK доповнено `routine` (корінь ланцюга рутини). Нащадки — `repeat` із тими самими `routine_id`/`slot_at`, що й корінь.
- CHECK форми замість старого останнього: `kind IN ('due','eve_before','leave_now')` → `item_id IS NOT NULL`; `kind = 'routine'` → `routine_id IS NOT NULL`; `kind = 'repeat'` → `item_id IS NOT NULL OR routine_id IS NOT NULL`; `digest_*` → `item_id IS NULL AND routine_id IS NULL`; `timer` → `routine_id IS NULL`, `item_id` довільний (як у `0004`). CASE вичерпний: кожен `kind` має гілку.
- Усі рядки, індекси `0004`/`0005` і тригер `trg_rem_digest_shape` — без змін і без втрат.
- **Лічильник `AUTOINCREMENT` переноситься.** Кнопки несуть id рядка (`rm:<id>:ok`, `src/reminders/render.ts`), обробник шукає лише за `(userId, id)`. Рецепт `CREATE new → INSERT SELECT → DROP → RENAME` ставить `seq = max(id)` вижилих, тож id видаленого найбільшого рядка (каскад «Не так») дістався б новому нагадуванню, і ✅ старого повідомлення закрив би чужу справу. Тому до `DROP`: `DELETE FROM sqlite_sequence WHERE name = 'reminders_new'; INSERT INTO sqlite_sequence(name, seq) SELECT 'reminders_new', seq FROM sqlite_sequence WHERE name = 'reminders'` (`RENAME` переносить рядок лічильника). Якщо D1 не дасть писати в `sqlite_sequence` (local чи preview, 4.1.c) — обхід: до `RENAME` вставити в нову таблицю рядок-заглушку з `id` = `seq` старої (коли `seq > max(id)`), що проходить CHECK і FK, і видалити його.
- Новий `ux_rem_routine_pending ON reminders(routine_id, slot_at) WHERE parent_id IS NULL AND routine_id IS NOT NULL AND status = 'pending'` — у слота не більше одного майбутнього кореня.

**`points_ledger`:** `ADD COLUMN routine_log_id INTEGER REFERENCES routine_logs(id) CHECK (routine_log_id IS NULL OR (reason = 'done' AND item_id IS NULL))`; `ux_ledger_routine_done ON points_ledger(routine_log_id) WHERE reason = 'done' AND routine_log_id IS NOT NULL` — одне «✅» на слот назавжди (`ux_ledger_done` за `item_id` тут нічого не тримає: `NULL ≠ NULL`).

**`routine_drafts`** — чернетка майстра, одна на користувача: `user_id` PK → `users(id)`; `routine_id` NULL (редагування наявної); `step` CHECK `kind, title, times, days, confirm`; `kind`, `title`, `times`, `days_mask` — NULL, доки не обрані; `expires_at`, `created_at` NOT NULL.

**`routine_inputs`** — повідомлення, які забрав майстер: `(user_id, tg_update_id)` PRIMARY KEY, `created_at`. Тригери `BEFORE INSERT` на `captures` і `capture_fixes`: такий `(user_id, tg_update_id)` уже є в `routine_inputs` → `RAISE(ABORT)`. Один простір `update_id`, як `capture_fixes` у Фазі 1 (`decisions.md`, В2 рев'ю 0.2).

`users`: `ack_taken_idx`, `ack_skip_idx` (пам'ять варіантів тостів, НФ-4); «+15 хв» бере наявний `ack_later_idx`.

### S4.1 · P1 · Схема й перебудова `reminders` (крок 4.1) 🔒

- **4.1.a** Given міграції 0001–0006, When прямий SQL, Then відхилено: `routines.kind='pill'`, `title` 65 символів, `title` з переносом рядка, `times='[]'`, `times='x'`, 7 часів, `days_mask` 0 і 128, `active=2`; `routine_logs.status='late'`, `missed` з `answered_at`, `taken` без `answered_at`, другий рядок того ж `(routine_id, scheduled_for)`; `reminders` з `item_id` і `routine_id` разом, `routine` без `routine_id`, `routine_id` без `slot_at`, `due` без `item_id`, `digest_morning` з `routine_id`; другий `pending` корінь того ж слота; `points_ledger` з `routine_log_id` і `reason='capture'`, другий `done` того ж `routine_log_id`.
- **4.1.b** Given база з рядками `reminders` усіх видів (`due`+`repeat`-ланцюг, `eve_before`, `leave_now`, `digest_*`, `cancelled`, `sent` з `tg_message_id`), When `0006`, Then кількість рядків і кожне поле кожного рядка збігаються з «до» (знімок до міграції, порівняння по `id`); `ON DELETE CASCADE` від `items` і між `parent_id`/`root_id` працює як до; `trg_rem_digest_shape` і всі індекси `0004`/`0005` є (`sqlite_master`); `sqlite_sequence.seq` для `reminders` після = до, і Given видалено рядок з найбільшим id, перший новий рядок після `0006` отримує id > будь-якого колишнього. *Мутанти: пропустити колонку в копіюванні; перебудова без перенесення лічильника — червоніють.*

- **4.1.d** НФ-3: функції `src/db/routines.ts` беруть `userId` першим; чужий `routine_id` → нічого не читає й не змінює. Закритий список винятків доповнено двома функціями `src/db/system.ts`: `listRoutinesToPlan` і `listUnansweredRoutineSlots` (cron по всіх; далі — з `user_id` рядка).
- **4.1.e** Тригер `routine_inputs`: Given `(u, 77)` у `routine_inputs`, When `INSERT` у `captures` або `capture_fixes` з `(u, 77)`, Then `ABORT`; з `(u, 78)` або `(інший u, 77)` — успіх.

## Майстер

Вхід — команда `/routines` (і рядок у меню команд). Без рутин — коротке пояснення й кнопки **[💊 Ліки] [🔁 Звичка]**; з рутинами — список (S4.7) і ті самі кнопки. Кроки чернетки: `kind` → `title` (текстом) → `times` → `days` → `confirm`. На кожному кроці є **[✖ Скасувати]**. Кожна кнопка майстра продовжує `expires_at = now + WIZARD_TTL_MS`.

### S4.2 · P1 · Нова рутина кнопками (крок 4.2)

- **4.2.a** When «💊 Ліки», Then `routine_drafts` (`kind='med'`, `step='title'`), відповідь: «Як назвати? Коротко, до 64 символів. Назву я нікуди не передаю — ні ШІ, ні розпізнаванню». Друга кнопка ➕, коли чернетка вже є, — замінює її (одна на користувача).
- **4.2.b** Given `step='title'`, When текст «  Вітамін D  », Then `title='Вітамін D'` (обрізано), `step='times'`, сітка годин 00–23 (6×4); 65+ символів або перенос рядка → «трохи коротше, в один рядок 🙂», крок не змінюється, але update забрано майстром (`routine_inputs`, 4.3.a).
- **4.2.c** Година → рядок хвилин `:00 :15 :30 :45` → час додано (сортування, повтор ігнорується) → «Час: 08:00, 20:00 · [➕ ще час] [Далі →]». На 6-му часі ➕ зникає.
- **4.2.d** «Далі →» → 7 перемикачів Пн…Нд (усі ввімкнені) + **[Щодня] [Будні]** + **[Далі →]**; 0 днів → тост «хоч один день», крок не змінюється.
- **4.2.e** Підсумок: «💊 Вітамін D · 08:00, 20:00 · щодня» **[✅ Зберегти] [✖]**. Час у тихих годинах — дописка «нагадаю й у тихі години: це ти обрав сам» (S4.5.h).
- **4.2.f** «Зберегти» → один `DB.batch`: `INSERT routines` (`active=1`, `escalate` = `kind='med'`) з чернетки й `DELETE` чернетки; подвійний тап → одна рутина (другий не знаходить чернетки → тост «уже збережено»). Перше нагадування планує cron (S4.4) — ≤ 1 хв.
- **4.2.g** «✖» на будь-якому кроці → чернетку видалено, «скасував, нічого не зберіг». Кнопка мертвої чи чужої чернетки → тост «майстер закрився — почнімо знову: /routines», без змін.
- **4.2.h** 20 рутин → ➕ дає тост про ліміт, чернетка не створюється.

### S4.3 · P1 · Межа з ШІ: назва — не запис (кроки 4.1 і 4.2) 🔒

Порядок обробки текстового повідомлення: (1) команда → команда; (2) жива чернетка (`expires_at > now`) у `step='title'` → назва; (3) вікно «Не так» → виправлення (S1.6); (4) інакше — захоплення (S1.x).

- **4.3.a** Given `step='title'`, When **будь-яке** повідомлення, яке забрав крок (прийнята назва «Магне B6 два рази», відхилена за 4.2.b, голосове чи пересилання за 4.3.e), Then в одному `DB.batch`: `INSERT routine_inputs (u, update_id)` + зміна чернетки (якщо назву прийнято). Немає рядка `captures`, `capture_fixes`, `items`, `ai_calls`, очка `capture`; мок Claude не викликано. У логах — довжина, не текст (НФ-2). Перевірка дубля до STT і ШІ (`isKnownUpdate`, `src/capture.ts`) рахує й `routine_inputs`: голосове йде у Whisper раніше за будь-який `INSERT`, тож тригер 4.1.e його не зупинить.
- **4.3.b** Повтор доставки того самого `update_id` — і поки чернетка ще в `title`, і після переходу на `times`, і після «Зберегти», і після ✖ — для прийнятої назви, відхиленої (65+ символів), голосового й пересилання: 0 рядків `captures`, жодної зміни назви, мок Claude і мок Whisper не викликані; відповідь Telegram — 200. Тримає `PRIMARY KEY` і тригер 4.1.e, а не `if`. *Мутанти: прибрати тригер на `captures` — «повтор після збереження» червоніє; писати `routine_inputs` лише для прийнятої назви — «повтор відхиленої після ✖» червоніє; прибрати `routine_inputs` з `isKnownUpdate` — «повтор голосового після ✖» кличе Whisper.*
- **4.3.c** Чернетка в `step` `times`/`days`/`confirm` → текст — звичайне захоплення (час і дні — лише кнопками), чернетка жива.
- **4.3.d** Мертва чернетка: текст о `expires_at + 1 с` → захоплення (Фаза 1); о `expires_at − 1 с` → назва.
- **4.3.e** Голосове чи пересилання в `step='title'` → `INSERT routine_inputs` (4.3.a), не йде у Whisper, не стає захопленням; відповідь «назву — лише текстом 🙂; якщо це був запис — надішли після майстра». Чернетка жива.
- **4.3.f** «Не так» і майстер — виграє останній намір: ➕ у майстрі (чи «✏️ Назва», S4.7) скидає відкрите вікно «Не так» (`captures.fix_requested_at = NULL`); «Не так» видаляє живу чернетку. Тест в обох порядках: наступний текст іде туди, що натиснуто останнім.
- **4.3.g** Охоронець промптів: мок Claude падає, якщо промпт містить назву засіяної рутини чи її `times`; проганяються захоплення, повтор `pending`, «Не так» — 0 падінь (НФ-2, «Медичні дані»). Статичний тест: модулі, що збирають промпт (`src/ai/**`), не імпортують `src/db/routines*`; `routines` немає в `items_fts`.
- **4.3.h** Текст про ліки **поза** майстром («купити вітамін D») — звичайний запис і йде в розбір: це текст, який людина сама написала в чат (`open-questions.md`, Фаза 1 → закрито тут, Р4.3).

## Планувальник і нагадування

Кожен тик cron, після планувальника записів і оглядів, до відправки: для кожної `active` рутини береться **найближчий слот** `slot_at ≥ now − LATE_MS` (за `times`, `days_mask`, `tz`) і створюється корінь `routine` (`fire_at = slot_at`, `attempt=1`, `max_attempts` = 4 при `escalate=1`, інакше 1), якщо для `(routine_id, slot_at)` ще немає **жодного** кореня — і `cancelled` теж (4.5.g, 4.5.k): інакше відмова Telegram давала б новий корінь і новий виклик щотику, доки слот у межах `LATE_MS`. Невідправлені корені, які прибирають зміна часу, днів, поясу чи пауза (4.7.c–e), **видаляються** (`DELETE` тих самих рядків, що були б `cancelled`): на них нічого не посилається (немає `sent`, нащадків, `tg_message_id`), і слот, що лишився в розкладі, планується знову. Наступний слот з'являється, коли поточний уже має корінь, — без поля «сплановано до».

### S4.4 · P1 · Слот за розкладом (кроки 4.1 і 4.2)

- **4.4.a** Given `med` 08:00, 20:00 щодня, Київ, now = 07:00 локально, When тик, Then один корінь `slot_at = fire_at` = 08:00 Київ (UTC ms), `max_attempts=4`; `habit` — `max_attempts=1`.
- **4.4.b** Given `days_mask` Пн–Пт, now = п'ятниця 21:00, Then корінь — понеділок 08:00.
- **4.4.c** Ідемпотентність: два тики підряд і два «одночасно» → один корінь (`ux_rem_routine_pending` + умова «немає кореня»). Після відповіді на слот 08:00 о 08:02 наступний тик не створює другого кореня 08:00 і планує 20:00 лише коли `08:00 < now − LATE_MS`.
- **4.4.d** Рутину створено о 08:03 з часом 08:00 → корінь 08:00 (у межах `LATE_MS`) і відправка цим тиком; створено о 08:06 → корінь — наступний слот.
- **4.4.e** `active=0` → нових коренів немає.
- **4.4.f** НФ-1: слот 03:30 на 2026-03-29 → 04:30 за Києвом (`2026-03-29T01:30Z`); на 2026-10-25 → перше входження (`2026-10-25T00:30Z`), один корінь. День тижня — локальний: now = `2026-11-20T22:30Z` (субота 00:30 Київ), рутина «лише сб, 00:45» → `2026-11-20T22:45Z`.
- **4.4.g** Нагадування рутини не залежить від `items` і боргу «через N хв від обробки» (`PROGRESS.md`): мить — фіксований `times`, не відлік від повідомлення.

### S4.5 · P1 · Нагадування і кнопки «прийняв ✅» / «пропущу» / «+15 хв» (крок 4.2) 🔒

Текст: «💊 <назва>» (`med`) чи «🔁 <назва>» (`habit`) з пулу ≥ 3 варіантів (`reminders.variant_idx`, НФ-4), назва екранована (НФ-9); повтор — м'якший варіант того ж пулу, без «ти не відповів». Кнопки: **[✅ прийняв]** (`habit`: **[✅ зробив]**) **[пропущу] [+15 хв]**.

- **4.5.a** `med`: ланцюг рівно 4 відправки, 5→15→30 хв від фактичного `sent_at` (S2.2.a–d — та сама `nextRepeat`); `habit` — 1, нащадка немає.
- **4.5.b** «✅» на будь-якій спробі → один `DB.batch`: `routine_logs` `taken` (`answered_at=now`), усі `pending` рядки слота → `cancelled`, натиснутий `sent` → `answered`, `points_ledger` +10 `done` з `routine_log_id`; кнопки знімаються, тост з пулу (`ack_taken_idx`).
- **4.5.c** Подвійний тап і «✅» з двох повідомлень слота (корінь і повтор) → один `routine_logs`, одне +10 (`UNIQUE` слота й `ux_ledger_routine_done`, не `if`). *Мутант: прибрати `ux_ledger_routine_done` — +20.*
- **4.5.d** «пропущу» → `skipped`, `pending` слота → `cancelled`, 0 очок, тост без оцінки («ок, цей раз без нього»).
- **4.5.e** «+15 хв» → натиснутий рядок `answered` (`WHERE status='sent'`), `pending` слота → `cancelled`, новий корінь `routine` того ж `slot_at`, `fire_at = now + 15 хв`, `attempt=1`; тост «нагадаю о HH:MM». Слот уже має `taken`/`skipped` → лише тост «уже записав».
- **4.5.f** Слот із `taken`/`skipped` → будь-яка кнопка дає тост «уже записав», БД без змін. Чужий `routine_id` чи рядок у `callback_data` → тост, без змін (S1.1.e).
- **4.5.g** У мить відправки рутина `active=0` або слот уже має відповідь → рядок `cancelled`, нічого не надіслано.
- **4.5.h** **Тиха ніч рутин не стосується:** слот 23:30 при тиші 23:00–08:00 → корінь і повтори йдуть вчасно. **Пауза стосується:** при `pause_until > now` рядок чекає; після паузи, якщо `now ≤ fire_at + ROUTINE_TTL_MS`, іде окремим повідомленням з кнопками, інакше `cancelled` без повідомлення й без `routine_logs`.
- **4.5.i** Анти-шум: рядок рутини ніколи не йде у зведення й не чекає ліміту 6/год, але записується `sent_as='single'` і входить у ліміт для решти (як огляд, `decisions.md` 3.0).
- **4.5.j** Тон: пули пушів і тостів рутин — ≥ 3 варіанти, проходять тест заборонених слів НФ-4; жодного числа пропусків у тексті.
- **4.5.k** 400/403 від Telegram на рядку рутини → `cancelled` і клас помилки з закритого списку 3.1.h (без сирого `description`); наступні тики не створюють нового кореня цього слота: 403 на корені 08:00 і тики 08:01…08:05 → 1 виклик Telegram і 1 корінь. 429/5xx — оренда знята, спроба наступним тиком (S2.3).

### S4.6 · P1 · Без відповіді — `missed`, мовчки (кроки 4.1 і 4.2)

Cron (`listUnansweredRoutineSlots`): слот, де немає `pending` рядків, **останній за `sent_at` рядок слота — `sent` з `attempt = max_attempts`** (ланцюг вичерпано, а не обірвано), його `sent_at ≤ now − MISSED_AFTER_MS` і немає `routine_logs`, → `INSERT routine_logs (missed) ON CONFLICT DO NOTHING`. Ознака — у самому ланцюгу, а не в `active` у мить прогону: ▶️ після паузи її не змінює. Обірваний ланцюг (пауза, TTL, 400/403) — не `missed`: людина не отримала всіх нагадувань.

- **4.6.a** `med`: 4 відправки без відповіді, `now = останній sent_at + 30 хв` → `missed`, `answered_at NULL`; жодного повідомлення, очок, зміни `reminders`. `habit`: 1 відправка + 30 хв → `missed`.
- **4.6.b** Пізніше «✅» на старому повідомленні → `missed` → `taken` (`UPDATE … WHERE status='missed'`), `answered_at=now`, +10 один раз; «пропущу» → `skipped`. `taken`/`skipped` назавжди.
- **4.6.c** Слот, жодна спроба якого не пішла (TTL, пауза рутини) → `routine_logs` не створюється.
- **4.6.d** `med` 08:00 надіслано (1 з 4), ⏸ о 08:10 (повтор → `cancelled`), ▶️ о 12:00, ще два тики → `routine_logs` слота порожньо, вечір 4.9.a його не рахує. Те саме — повтор, скасований TTL (4.5.h) чи 400/403 (4.5.k). *Мутант: умова «є `sent` без відповіді» замість «останній — `attempt = max_attempts`» — червоніє.*
- **4.6.e** Два прогони поспіль → один рядок (`UNIQUE`).

## Список, редагування, пауза

### S4.7 · P2 · `/routines`: змінити час, дні, назву; пауза (крок 4.2)

- **4.7.a** `/routines` → рядок на рутину: «💊 Вітамін D · 08:00, 20:00 · щодня» (на паузі — «⏸ …»), кнопка на кожну → картка **[⏰ Час] [📅 Дні] [✏️ Назва] [⏸ Пауза | ▶️ Увімкнути] [← Список]**.
- **4.7.b** «✏️ Назва» → чернетка з `routine_id`, `step='title'`; далі як 4.3 (вся межа з ШІ діє й тут) → `UPDATE title`, `updated_at`. Нові пуші й повтори вже відправленого ланцюга беруть нову назву (текст збирається в мить відправки).
- **4.7.c** «⏰ Час» / «📅 Дні» → кроки 4.2.c / 4.2.d з порожнім / поточним вибором → «Зберегти» → `UPDATE`; в тому ж batch `pending` **корені, ще не відправлені**, цієї рутини → `DELETE` (S4.4); ланцюг, що вже йде (є `sent`), не чіпається. Новий слот — наступним тиком; слот, що лишився в розкладі (дні змінено, час той самий), планується знову.
- **4.7.d** «⏸ Пауза» → `active=0`, невідправлені корені рутини → `DELETE`, `pending` повтори → `cancelled`; «▶️» → `active=1`, найближчий слот наступним тиком (S4.4); слот, що минув під час паузи, не нагадується.
- **4.7.e** Зміна поясу (`/tz`, S3.8) → у тому ж batch `pending` невідправлені корені рутин → `DELETE` і нові корені за новим `tz` (як корені планувальника записів, `decisions.md` 3.0 В3; `DELETE` замість `cancelled` — S4.4).
- **4.7.f** Чужий `routine_id` у кнопці картки → тост «не знайшов», без змін.

## Огляди

### S4.8 · P2 · Ранок: рутини дня одним рядком (крок 4.2)

- **4.8.a** Given ранковий огляд і так іде (S3.2/S3.3), а сьогодні (локально) є активні рутини, Then один рядок після подій і справ: «💊 Сьогодні: Вітамін D 08:00 ✓, 20:00 · 🔁 Прогулянка 19:00» — порядок за першим часом, `✓` лише біля `taken`; `missed`/`skipped` не позначаються ніяк.
- **4.8.b** Понад 5 рутин → «…ще N». Без рутин дня — рядка немає.
- **4.8.c** Рутини самі не роблять ранок непорожнім: лише рутини → огляд за правилом порожнього ранку S3.3 (Р4.7).
- **4.8.d** Ранок не змінює `reminders` рутин (на відміну від S3.4 для записів): пуш 08:00 іде своїм ходом.

### S4.9 · P2 · Вечір: «прийнято N з M» без провалів (крок 4.2)

- **4.9.a** Given у `routine_logs` за локальну добу `M` рядків (`taken`+`skipped`+`missed`), з них `N ≥ 1` `taken`, Then рядок «💊 рутини: N з M ✅»; `N = M` → «💊 рутини: усі ✅». Слоти без рядка (ще попереду, ланцюг ще йде) не рахуються.
- **4.9.b** `N = 0` → рядка немає (жодного «0 з 3»). Назви пропущеного не перелічуються ніколи.
- **4.9.c** +10 за рутини входять в «очки дня» S3.5 через `points_ledger` без окремого рядка.
- **4.9.d** Доба — межі `dayBounds(tz)` за `scheduled_for`, не за `answered_at`: пізнє «✅» вчорашнього слота сьогодні не потрапляє в сьогоднішнє M.

## Рішення

Короткі; один рядок-посилання — у `decisions.md`.

- **Р4.1 Рутини — у черзі `reminders` через перебудову таблиці в `0006`, а не окрема черга.** CHECK `0004` не пускає рядок без `item_id`; окрема черга повторила б тишу, паузу, оренду, 403/429 і ліміт. Перебудова — один раз, з репетицією на preview (4.1.c). Як огляди в Фазі 3 (`decisions.md`, 3.0).
- **Р4.2 Стан майстра — таблиця `routine_drafts` (одна на користувача, TTL 15 хв), назву забирає лише крок `title`.** Час і дні — кнопки, тож перехоплювати текст на інших кроках не треба: випадкова думка людини посеред майстра лишається записом.
- **Р4.3 Текст про ліки поза майстром — звичайний запис** (закриває питання Фази 1): людина сама написала його в чат; заборона НФ-2 стосується даних таблиць `routines`/`routine_logs`.
- **Р4.4 `routine_inputs` + тригери на `captures`/`capture_fixes`** — повтор доставки будь-якого повідомлення кроку `title` (і відхиленої назви, і голосового) інакше став би захопленням і поніс би назву ліків у Claude чи Whisper (повтор `pending` теж).
- **Р4.5 Тиха ніч не стосується рутин, `/pause` — стосується.** Час рутини людина обрала сама, кнопкою, — це згода; тиша захищає від несподіваних пушів. Пауза — свіже явне «не чіпай». `important` записи й далі мовчать уночі (рішення Фази 2 не змінене). Робоче припущення: `open-questions.md`, Фаза 4.
- **Р4.6 Огляди (код, без ШІ) читають `routines`/`routine_logs`.** Уточнює принцип 3 і «Поза межами» `phase-3.md`: правило 4 `CLAUDE.md` — про промпт ШІ; охоронець 4.3.g тримає саме його.
- **Р4.7 Ранок лише з рутинами — не привід надсилати огляд:** пуші рутин прийдуть самі, дубль — шум. Перегляд — після 2 тижнів.
- **Р4.8 `routine_logs.user_id` та `id` — відхилення від `PLAN.md`:** `user_id` — НФ-3, `id` — для `points_ledger.routine_log_id`.
- **Р4.9 `missed` пише cron через 30 хв після останньої відправки; кнопки старого повідомлення діють і після `missed`.** Факт «прийняв пізніше» — правда, яку варто зберегти; людина нічого про `missed` не чує.
- **Р4.10 Корінь — лише найближчий слот кожної рутини**, без поля «сплановано до»: вибірка — один запит на тик, ланцюг самовідновлюється за хвилину (як огляди, `decisions.md` 3.1).
- **Р4.11 Розбіжності з промптами 4.1/4.2 — виграє спека.** Немає `planDay(userId, date, tz)` і планування «на завтра» в годинному самовідновленні — лише корінь найближчого слота щотику (Р4.10); мутант M1 промпту 4.1 читати як «прибери `days_mask` з вибору найближчого слота» (червоніє 4.4.b). Команди `/routine` немає: майстер і список — одна `/routines` (S4.2, S4.7). Майстер забирає текст лише на кроці `title`, а не «поки активний» (4.3.c, Р4.2).

## Поза межами

- Видалення рутини (лише пауза), архів, історія прийомів кнопкою, `/today` з рутинами, `/export` з рутинами (`open-questions.md`).
- Тижневий огляд із рутинами; статистика «за місяць»; будь-яке окреме число пропусків (знаменник M у 4.9.a — не воно).
- Дози, запас таблеток, «закінчуються ліки», інтервали «кожні 8 год», рутини не за днями тижня (через день).
- Медичні поради будь-якого роду в текстах («якщо пізно — пропусти»).
- Повний розподіл очок і бонуси за рутини — Фаза 6; тут лише `done` +10.
- Голосом або вільним текстом створити рутину («нагадуй пити вітамін о 8») — ні: ШІ не бачить рутин і не діє (правило 3).
- Зміна поведінки записів `important` у тиху ніч.

## Борг, що стосується Фази 4

- «Через N хв рахується від обробки, а не від `message.date`» (`PROGRESS.md`, 3.3) рутин не зачіпає (4.4.g) і лишається в «Борг».
- R-2 Д4 (400 → `cancelled` без класу помилки): для рутин закривається критерієм 4.5.k (пуш несе назву людини — зламаний HTML імовірний, а тиха втрата нагадування про ліки найдорожча); для `due`, повторів і зведень лишається в «Борг».
