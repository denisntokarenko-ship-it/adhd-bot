# Фаза 2 — Нагадування

Читати разом з [00-common.md](00-common.md) (особливо НФ-1, НФ-3, НФ-4, НФ-6, НФ-7, НФ-9). Кроки: 2.1 черга й планувальник · 2.2 відправка з cron, кнопки, очки, ліміт на годину · 2.3 події, дорога, дата «день + частина доби» · 2.4 тиша, пауза, `/quiet`, тексти-варіації. Зріз [phase-2-dates-texts.md](phase-2-dates-texts.md) (S2.8, S2.9.e–g, S2.10–S2.12: дати, `/pause`, тексти, `/quiet`, числівники) читати разом.

## Задача

Запис із датою перетворюється на нагадування, яке приходить само, у потрібну мить і без шуму. Людина закриває його однією кнопкою; якщо не закрила — важливе повторюється рівно чотири рази й замовкає, звичайне нагадує один раз. Уночі й на паузі бот мовчить, а потім говорить один раз, а не десять. Жодного «ти пропустив»: після останньої спроби запис просто лишається відкритим і піде у вечірній огляд (Фаза 3).

Фаза закрита, коли на preview: «через 2 хв важливо подзвонити мамі» дає 4 повтори без відповіді, ✅ на другому зупиняє решту й дає +10; подія «завтра 10:00» дає «навечір» і «час виходити» з дорогою; у тихі години нічого не приходить, а після них — одне зведення.

Порядок історій = порядок реалізації. P1 разом — працюючі нагадування з кнопками; P2 — ліміт шуму, події, тиша й варіації текстів; P3 — `/quiet`, якість дат з голосу.

## Принципи

- **Нагадування — похідний стан.** Рядок `reminders` випливає з запису й налаштувань; його створює планувальник у cron, а не код захоплення. Новий шлях запису (текст, голос, пересилання, повтор, «не так») нічого не забуде.
- **Краще двічі, ніж жодного.** Тиха втрата гірша за рідкісний дубль: рядок не стає `sent`, доки не відправлений — його «орендують» (lease).
- **Тиша — мовчання без боргу:** спроби не витрачаються, тексти нейтральні (НФ-4). ШІ в нагадуваннях не бере участі (єдина дотична — правило дат у промпті розбору, S2.8).

## Схема (міграція `0004_reminders.sql`, крок 2.1)

`users.quiet_from`, `quiet_to`, `pause_until` **уже є** з `0001` (дефолт 23:00–08:00; рівні = тихих годин немає). Нових колонок для тиші немає; нові лише шість `users.ack_*_idx` (пам'ять варіанта підтверджень — колонка на пул, НФ-4; S2.10.b).

**`reminders`** — одна запланована відправка:

| Колонка | Тип і обмеження |
|---|---|
| `id` | INTEGER PK AUTOINCREMENT |
| `user_id` | NOT NULL → `users(id)` |
| `item_id` | → `items(id)` **ON DELETE CASCADE** (заміна записів «не так» прибирає нагадування сама); NULL лише для `digest_*`/`timer` |
| `kind` | CHECK `due, eve_before, leave_now, repeat, timer, digest_morning, digest_evening, digest_weekly` (повний перелік плану: SQLite не міняє CHECK без перебудови) |
| `fire_at` | INTEGER NOT NULL (UTC ms) |
| `attempt`, `max_attempts` | NOT NULL; `attempt` 1..4, `max_attempts` 1..4, `attempt ≤ max_attempts` |
| `status` | CHECK `pending, sent, answered, cancelled`, дефолт `pending` |
| `parent_id` | → `reminders(id)` ON DELETE CASCADE: попередня спроба ланцюга; NULL у кореня |
| `root_id` | перший рядок ланцюга; NULL у кореня; `(parent_id IS NULL) = (root_id IS NULL)`, `(kind='repeat') = (parent_id IS NOT NULL)` |
| `lease_until` | INTEGER NULL — оренда |
| `sent_at`, `sent_as`, `tg_message_id` | `sent_as` CHECK `single, summary`; `(status IN ('sent','answered')) = (sent_at IS NOT NULL)`; `(sent_at IS NULL) = (sent_as IS NULL)` |
| `variant_idx` | INTEGER CHECK ≥ 0 — варіант тексту |
| `created_at` | INTEGER NOT NULL |

CHECK: `kind IN ('digest_morning','digest_evening','digest_weekly','timer') OR item_id IS NOT NULL`.

- Індекси: `ix_rem_due (status, fire_at)`; `ix_rem_item (item_id)`; `ix_rem_user_sent (user_id, sent_at)` (лічильник години).
- **Ідемпотентність у БД, не в коді (НФ-7):** `ux_rem_root` UNIQUE `(item_id, kind, fire_at)` WHERE `parent_id IS NULL AND status <> 'cancelled'` (скасований корінь не блокує перепланування в ту саму мить, S2.7.b); `ux_rem_child` UNIQUE `(parent_id)` WHERE `parent_id IS NOT NULL` — у рядка не більше одного нащадка, хоч би скільки разів «відпрацювала» оренда.
- Відхилення від `PLAN.md`: UNIQUE із `routine_id` у SQLite не тримає ідемпотентність (`NULL ≠ NULL`), а `routine_id` у Фазі 2 порожній — колонку додасть Фаза 4 через `ALTER`; `digest_*` отримають власний частковий індекс у Фазі 3.
- `items`: `ADD COLUMN travel_asked_at INTEGER` (питання про дорогу задано раз) · `ADD COLUMN planned_at INTEGER` (планувальник запис опрацював — навіть коли рядків вийшло 0) · індекс `ix_items_status_due (status, due_at)` для вибірки планувальника.
- `points_ledger`: частковий UNIQUE `ux_ledger_done ON (item_id) WHERE reason = 'done'` — одне «зроблено» на запис назавжди, у БД.

## Звідки береться нагадування (планувальник)

Cron щохвилини (S2.3, крок 1) бере записи `open` з `due_at` і `planned_at IS NULL` (`ORDER BY id DESC LIMIT 50`) і створює рядки за таблицею; тим самим `DB.batch` ставить `planned_at = now` — **навіть коли рядків 0** (мить позаду): «мертві» записи не повертаються щотику й не витісняють нових із `LIMIT`. Опрацьований запис заново не планується: далі ним керують кнопки й відповідь про дорогу. Рядок `kind` створюється, лише якщо кореня цього `kind` для запису ще немає (будь-який статус): відповідь про дорогу до першого тику не заглушає `eve_before` (2.1.j).

| Запис (`status='open'`, `due_at` не NULL) | Рядки |
|---|---|
| будь-який `kind`, крім `event`, з часом, `normal` | `due` о `due_at`; `max_attempts=1` |
| те саме, `important` | `due` о `due_at`; `max_attempts=4` (ланцюг `repeat`) |
| `all_day` (будь-який `kind`, крім `event` з часом) | `due` о `morning_at` тієї локальної доби; `max_attempts` за `priority` |
| `event` з часом | `eve_before` о 20:00 попереднього дня й `leave_now` о `due − travel − 15 хв` (`travel` = `travel_min ?? 0`); `max_attempts=4` для `leave_now`, `1` для `eve_before` |
| `note` без дати, `done`, `released`, `due_at` NULL | нічого |

Правила планування:
- Рядок, чий `fire_at < now − LATE_MS`, **не створюється**: людина щойно сама це написала, пінг «у минулому» — шум. Допуск `LATE_MS` потрібен, щоб «через хвилину» не загубилось між тиками.
- `eve_before` створюється лише якщо 20:00 попереднього дня ще попереду (> `now + 5 хв`). Подію, створену пізніше, «навечір» не пінгує: питання про дорогу (S2.7) іде в ту ж мить і містить день, час і назву — це і є «в момент створення» без другого пуша за хвилину після квитанції.
- `nextRepeat(row)` (чиста): attempt 1→2 через 5 хв, 2→3 через 15, 3→4 через 30 від `sent_at`; після `attempt = max_attempts` — `null`. Для `leave_now` наступна спроба, що випала б після `due_at` події, **не створюється**: повтор «час виходити» після початку події — докір, не допомога.
- Подія не стає `important` автоматично (закриває питання з Фази 1): `priority` не змінюється, а `leave_now` ескалується завжди (так працює «події — повтор до відповіді» з `PLAN.md`); `eve_before` — один раз.
- Усі `INSERT` планувальника — `ON CONFLICT DO NOTHING`.

### S2.1 · P1 · Схема й планувальник (крок 2.1) 🔒

- **2.1.a** Given міграції 0001–0004, Then `reminders` має CHECK-и вище; прямий SQL: `status='done'`, `kind='ping'`, `attempt=5`, `attempt>max_attempts`, `kind='repeat'` без `parent_id`, `parent_id` без `root_id`, `status='sent'` без `sent_at`, `item_id=NULL` для `due` — усе відхилено.
- **2.1.b** Given запис `important` з `due_at = T`, When планувальник, Then один рядок `due` (`fire_at=T`, `attempt=1`, `max_attempts=4`, `status='pending'`); Given `normal` — `max_attempts=1`.
- **2.1.c** Ідемпотентність: Given планувальник відпрацював двічі поспіль (і двічі «одночасно»), Then рядків рівно стільки, скільки в одному прогоні (UNIQUE, не `if`); прямий дубль `(item_id, kind, fire_at)` кореня → конфлікт, `parent_id` двічі → конфлікт. *Мутант: прибрати `ON CONFLICT DO NOTHING` або індекс — тест червоніє.* Скасований корінь такого дубля не блокує (S2.7.g).
- **2.1.d** `all_day` на 2026-11-21 при `morning_at=09:00` Київ → `fire_at = 2026-11-21T07:00Z`; на 2026-03-29 (перехід) — 09:00 за місцевим (`06:00Z`), без втрати й дубля.
- **2.1.e** `fire_at < now − LATE_MS` → рядок не створюється; `fire_at = now − 60 с` → створюється (і піде найближчим тиком).
- **2.1.f** Запис `done`/`released`/без `due_at` → нічого; планувальник не чіпає записи з `planned_at` (скасовані й відповідані рядки не відроджує).
- **2.1.g** Видалення запису (заміна «не так») каскадом прибирає його `reminders` (D1 тримає FK): тест із `pending`-рядком і його нащадком.
- **2.1.h** Ізоляція (S1.1.e): функції `src/db/reminders.ts` беруть `userId` першим; чужий `item_id` → нічого не створює й не змінює. Єдині виняткові функції без `userId` — `claimDueReminders`, `listUnplannedItems` у `src/db/system.ts` (оновлений закритий список НФ-3).
- **2.1.i** Given 50 записів із минулою мить (`all_day` після `morning_at`, час спливло) і один новий (найбільший `id`), When один тик, Then новий має рядок, усі 50 — `planned_at`, наступні тики їх не повертають. *Мутант: вибірка без `planned_at` або `ORDER BY id` — новий без нагадування.*
- **2.1.j** Given подія «завтра 10:00», `tr` відповіли **до** першого тику (`leave_now` є, `planned_at` порожній), When планувальник, Then `eve_before` створено, `leave_now` один. *Мутант: перевірка «є рядок запису» замість `(item, kind)` — `eve_before` губиться.*

## Ескалація

### S2.2 · P1 · Повтори: рівно 4 для важливого, 1 для звичайного (кроки 2.1 і 2.2)

- **2.2.a** Given `important`, `due` відправлено о `t0` (`sent_at`), When рядок відправлено, Then в тій самій транзакції закриття створено `repeat` (`attempt=2`, `parent_id`, `root_id`, `fire_at = t0 + 5 хв`); після його відправки о `t1` — `attempt=3`, `t1 + 15 хв`; після нього о `t2` — `attempt=4`, `t2 + 30 хв`.
- **2.2.b** Після відправки `attempt=4` нащадка немає: рівно 4 відправки, ніколи 5 (`attempt < max_attempts`, не `≤`). Запис лишається `open`, жодного повідомлення «ти не відповів», жодного лічильника; Фаза 3 бачить «ланцюг вичерпано» як рядок `status='sent'` **без нащадка** — це і `attempt = max_attempts`, і `leave_now`, обірваний перед `due_at` (2.2.e), якого умова `attempt = max_attempts` не впіймала б. *Мутант: `<` → `≤` — червоніє.*
- **2.2.c** `normal`: після відправки `due` нащадка немає; статус `sent`. Пізніше натиснули кнопку — `answered`.
- **2.2.d** Затримка рахується від **фактичної** відправки: `due` о 10:00 пішло о 10:07 (cron лежав) → друга спроба о 10:12, не о 10:05.
- **2.2.e** `leave_now` події о 10:30 з дорогою 15 хв → `fire_at` 10:00; спроби 10:00 (1), 10:05 (2), 10:20 (3); наступна о 10:50 > 10:30 → не створюється; спроб 3, не 4; третя `sent` без нащадка = «вичерпано» (2.2.b).
- **2.2.f** Повтор не створюється, якщо запис уже не `open` на мить відправки (S2.5).
- **2.2.g** `repeat` ніколи не йде в тихий час (S2.9) і не «горить» під час нього: спроба не витрачається.

## Відправка

### S2.3 · P1 · Cron відправляє (крок 2.2)

Порядок прогону (оновлює «Архітектуру»): **серце → пінг монітора → нагадування → підбір pending-захоплень** (`processPending`, S1.5.g). Нагадування перед підбором: підбір робить до 3 довгих викликів ШІ/STT і може з'їсти хвилину, а нагадування — найчутливіше до часу. Кожна частина в окремому `try/catch`: збій одної не гасить інших і пінг.

Нагадування за прогін: (0) `STALE_MS`: старші за 48 год → `cancelled` без повідомлень; (1) планувальник (до 50 записів, S2.1); (2) множина користувачів у режимі тиші (S2.9) → їхніх рядків не беремо; (3) `claimDueReminders(now, 50, excludeUserIds)`: одним `UPDATE … RETURNING` рядки `pending` з `fire_at ≤ now`, чия оренда вільна, отримують `lease_until = now + LEASE_MS` — два прогони не заберуть той самий (атомарність `RETURNING` у D1 крок 2.1 перевіряє живцем, висновок — у «Рішення»); (4) по користувачах: перевірка запису, добір пачки (S2.6), відправка, закриття; (5) нерозіслані рядки (бюджет вичерпано) — оренда знімається, наступний тик їх підбере.

- **2.3.a** Given `pending` з `fire_at ≤ now`, When cron, Then повідомлення в чат користувача (приватний), текст з назвою (екранованою, НФ-9) і кнопками ✅ ⏰ 🗑 (на `eve_before` — 👍 ⏰ 🗑, 2.4.l); рядок → `sent`, `sent_at`, `sent_as='single'`, `tg_message_id`, `variant_idx`.
- **2.3.b** Рядок закривається **після** відправки: збій процесу між `sendMessage` і `UPDATE` лишає `pending` з орендою; через `LEASE_MS` рядок підбирається знову (допустимий дубль, див. «Принципи»). *Мутант: позначати `sent` до відправки — тест «збій після claim» червоніє (повідомлення втрачено).*
- **2.3.c** Помилки Telegram: 429 (з `retry_after`) і 5xx/мережа → оренда знята, `fire_at` не змінюється, спроба не витрачена; 400/403 (чат не існує, бот заблоковано) → `cancelled` + лог з id рядка (без тексту); інакше після 48 год рядок прибере `STALE_MS`.
- **2.3.d** Запис на мить відправки не `open` (done/released/видалений) → рядок `cancelled`, повідомлення нема. Перевірка — безпосередньо перед `sendMessage`.
- **2.3.e** Бюджет: після `RUN_BUDGET_MS` нових відправок немає; решта чекає тику. Прогін порожньої черги — один запит `claim`, без записів у БД.
- **2.3.f** Користувач у режимі тиші: його рядки не беруться, лічильників спроб не торкаємось (S2.9). Збій планувальника/черги не гасить пінг монітора й не зупиняє `processPending` (тест 0.3.f для черги нагадувань — борг R-0 закрито тут).
- **2.3.g** `/health` додає `reminders: {due: N}` — кількість `pending` з `fire_at ≤ now`; без персональних даних.

## Кнопки

### S2.4 · P1 · ✅ ⏰ 🗑 і очки (крок 2.2) 🔒

Дані кнопок: `rm:<reminder_id>:<дія>` (≤ 64 байт), дії `ok`, `ack`, `later`, `s15`, `s60`, `tom`, `back`, `rel`. Усі callback-и (`rm:`, `tr:`, `sm:`, `pz:`, `qt:`) — лише приватний чат; `rm:`, `tr:`, `sm:` — лише власник: кожен запит несе `user_id` (НФ-3), `tr:<item_id>` звіряє `items.user_id`, `sm:<message_id>` шукає за `(user_id, tg_message_id)` (id повідомлення унікальний лише в межах чату); чужий id → «не знаю такого» без змін. `ok` на рядку `eve_before` (стара клавіатура, зведення) обробляється як `ack`: «прийняв» не закриває подію.

- **2.4.a** ✅ Given відкритий запис, When `ok`, Then одним `DB.batch`: `items.status='done'`, `done_at=now`; усі `pending` рядки запису → `cancelled`; натиснутий → `answered`; `points_ledger(+10, 'done', item_id)`. Повідомлення редагується: «✅ <b>назва</b> — зроблено» без кнопок.
- **2.4.b** Повторний ✅ (подвійний тап, старе повідомлення, інше повідомлення того ж запису): стан не змінюється, очок немає, відповідь дружня («це вже зроблено 👍», пул ≥ 3). Захист у БД: `ux_ledger_done`; перед очками перевірка статусу — лише оптимізація. *Мутанти: прибрати перевірку/індекс → подвійне +10 → червоніє.*
- **2.4.c** ✅ не залежить від того, вчасно чи пізно: +10 і за запізнілий, і за вчасний; жодних «з запізненням», бонусів за точність (НФ-4, правило 6).
- **2.4.d** ⏰ показує підменю: клавіатура повідомлення (не нове повідомлення) → `[+15 хв] [+1 год] [Завтра о 09:00] [← назад]`; час «завтра» бере `users.morning_at`. `back` повертає ✅ ⏰ 🗑.
- **2.4.e** `s15`/`s60`/`tom`: `pending` рядки **цього ланцюга** (`COALESCE(root_id,id)` натиснутого) → `cancelled`; натиснутий `sent` → `answered`; новий корінь того ж `kind` (`due`/`eve_before`/`leave_now`; для `repeat` — kind кореня), `attempt=1`, `fire_at = now + 15 хв | now + 1 год | завтра`, `max_attempts` за правилами планувальника; `items.snooze_count + 1`; `items.due_at` не змінюється. Інші ланцюги запису (скажімо, `leave_now` після ⏰ на `eve_before`) не зачеплені. Повідомлення: «⏰ Ок, нагадаю <день і час>», без кнопок.
- **2.4.f** ⏰ двічі (подвійний тап): `UPDATE … WHERE status='sent'` зачепив 0 рядків → нового кореня нема, відповідь «вже відклав». `snooze_count` росте рівно на 1.
- **2.4.g** «Завтра»: `now = 2026-11-20T22:30Z` (00:30 сб) → нд 2026-11-22 09:00 Київ (`07:00Z`), а не сьогодні о 09:00; `2026-03-27T22:00Z` (00:00 сб 28.03) → нд 29.03 09:00 за місцевим, уже літній (`06:00Z`).
- **2.4.h** 🗑 `rel`: `status='released'`, усі `pending` запису → `cancelled`, натиснутий → `answered`; текст «Відпустив. Знайдеш пошуком, якщо що»; очок немає (`release` — Фаза 6). Запис не видаляється з БД.
- **2.4.i** Натиск на запис, що вже `done`/`released`, іншою дією (⏰, 🗑): нічого не змінюється, відповідь за станом («це вже зроблено 👍» / «вже відпущено»).
- **2.4.j** Редагування повідомлення (прибрати кнопки) — best effort: його помилка не скасовує зміну стану й не ламає `answerCallbackQuery`.
- **2.4.k** У коді немає загальної `add(delta, reason)`; експорти `src/db/points.ts` (охоронець S1.9.e) доповнені рівно одним: очко `done`.
- **2.4.l** `eve_before`: кнопки 👍 ⏰ 🗑, ✅ немає. `ack` лише ставить натиснутий рядок `answered` (запис, інші ланцюги, очки не зачеплені), повідомлення → «👍 <b>назва</b> — ок» без кнопок; повтор — без змін. Given `eve_before` і `pending` `leave_now`, When 👍 (або `ok` зі старої клавіатури), Then запис `open`, `leave_now` `pending`, 0 рядків у `points_ledger`. *Мутант: `ok` на `eve_before` закриває запис — червоніє.*
- **2.4.m** Чужий `item_id` у `tr:` і чужий `message_id` у `sm:` (той самий `tg_message_id` у чаті іншого користувача) → «не знаю такого», жодного рядка не змінено.

## Гонки

### S2.5 · P1 · Cron двічі, ✅ під час відправки, довгий прогін (крок 2.2)

- **2.5.a** Cron двічі в ту саму хвилину (два прогони паралельно, один `now`; мок Telegram рахує виклики): кожен `pending` рядок відправлено рівно один раз; другий прогін бачить оренду й пропускає. Тест на реальному D1 з `Promise.all`.
- **2.5.b** ✅ між `claim` і відправкою: перед `sendMessage` перевірка запису (2.3.d) → повідомлення нема, рядок `cancelled`.
- **2.5.c** ✅ між `sendMessage` і закриттям рядка (повтор уже пішов): закриття `UPDATE … WHERE status='pending'` зачепило 0 рядків; бот робить `deleteMessage` на щойно надіслане (best effort) і **не** створює нащадка (`INSERT … SELECT` умовний: `status='sent'` і запис `open`); очок не нараховується вдруге.
- **2.5.d** Прогін довший за хвилину: прогін A тримає оренду на 50 рядків; тик B о +60 с (A ще працює, оренда не збігла) їх не бере; після `RUN_BUDGET_MS` A сам знімає оренду з нерозісланих; якщо A впав — рядки підбере B після `LEASE_MS`, найгірше — один зайвий дубль на рядок.
- **2.5.e** ✅ і ⏰ натиснули майже одночасно (дві різні відповіді на одне повідомлення): виграє перша транзакція; друга бачить `done` (2.4.i) і не створює нового кореня «з майбутнього».

## Анти-шум

### S2.6 · P2 · Не більше 6 окремих пушів на годину, решта — зведенням (крок 2.2)

Лічильник — з `reminders`: окремі = рядки `sent_as='single'` із `sent_at > now − 1 год`; зведення = `DISTINCT tg_message_id` з `sent_as='summary'`. Питання про дорогу (S2.7) і відповіді на кнопки — не пуші, вони розмова.

Добір для користувача (`selectBatch`, чиста функція; рядки впорядковано: `important` перед `normal`, далі `fire_at`, `id`):

1. «Запізнілі» = `fire_at ≤ now − LATE_MS` (причина — тиша, пауза, збій cron). Якщо запізнілих ≥ 2 **або** ≥ 2 `repeat`-рядків, чий батько пішов зведенням (`parent.sent_as='summary'`: повтори групи не розсипаються на окремі пуші) → **усе, що зараз у черзі користувача** (запізнілі й свіжі), йде одним зведенням: пуш слідом за зведенням — шум. Один запізнілий — як звичайний. Якщо зведення в останню годину вже було — рядки чекають (як у п.3).
2. Інакше — окремо, поки `PUSH_SINGLE_PER_HOUR` не вичерпано.
3. Що не влізло в окремі → одне зведення, якщо в останню годину зведення ще не було; інакше рядки чекають (`pending`, спроба не витрачена) до звільнення вікна.

- **2.6.a** 8 свіжих рядків одного користувача за годину → 6 окремих + 1 зведення з двома; 9-й в ту ж годину чекає. *Мутант: поріг 6 → 60 — червоніє.*
- **2.6.b** Зведення: заголовок (пул ≥ 3) + до `SUMMARY_LINES`=5 рядків `• <b>назва</b> — час`, решта «…ще N» і кнопка «Показати ще N» (`sm:<message_id>:more:<зсув>` показує наступні ≤ 5 зі своїми ✅); під кожним показаним рядком кнопка «✅ <номер>» (`rm:<id>:ok`; для `eve_before` — «👍 <номер>», `rm:<id>:ack`) і внизу «⏰ Усе на +1 год» / «⏰ Усе на завтра» (`sm:<message_id>:s60|tom`: усі `sent` рядки цього повідомлення). 🗑 у зведенні немає: відпускання лише поодинці.
- **2.6.c** Усі рядки зведення → `sent`, `sent_as='summary'`, спільний `tg_message_id`; ланцюги `repeat` продовжуються (нащадок кожного рядка за `nextRepeat`), але їхні нащадки йдуть зведенням-повтором (п.1), не пушами.
- **2.6.d** Зведення ≤ 4096 (НФ-9), екранування; порожнього зведення не буває.
- **2.6.e** `selectBatch` — чиста функція; тести не торкаються БД. Приклади: 2 запізнілих + 1 свіжий → одне зведення з трьох; 1 запізнілий + 7 свіжих → 6 окремих + зведення з двох.
- **2.6.f** Три `important`, утримані вночі: 08:00 одне зведення; 08:05 нащадки (`parentSentAs='summary'`) чекають; 09:00 одне зведення повторів — 2 повідомлення за 65 хв, у ковзному вікні 1 год не більше одного. *Мутант: без `parentSentAs` у п.1 — о 08:05 три пуші, 8 за годину.*

## Події

### S2.7 · P2 · «Скільки добиратись?», напередодні, «час виходити» (крок 2.3)

- **2.7.a** Given квитанція про `event` з часом (не `all_day`), Then одразу після неї — окреме повідомлення з питанням у пулі ≥ 3 варіантів, у якому день, час і назва події; кнопки `0 / 15 / 30 / 60 хв` (`tr:<item_id>:<хв>`). Питання задається раз на подію (`items.travel_asked_at`, захоплення `UPDATE … WHERE travel_asked_at IS NULL`); повтор доставки update — без другого питання. Якщо повтор розбору (S1.5) відправляє квитанцію пізніше — питання йде слідом за нею, а не за часом події.
- **2.7.b** Відповідь `tr`: `items.travel_min = N`; `pending` `leave_now`-ланцюги запису → `cancelled`; новий корінь `leave_now` о `due − N − 15 хв` (`max_attempts=4`). Якщо ця мить уже позаду, але `due_at > now` — `fire_at = now` (людина щойно сказала, що дорога дальша, і ще встигає); якщо `due_at ≤ now` — нічого. `NULL` і `0` — те саме N: повторна відповідь з тим самим N (і перша «0» на `NULL`) при наявному `pending` `leave_now` — без змін; з іншим — перепланування без дублів (рівно один `pending` `leave_now`). Відповідь, що прийшла до першого тику планувальника, лише створює `leave_now` — решту (`eve_before`) планувальник додасть сам (2.1.j). *Мутант: перепланування без скасування — тест 30→60 червоніє.*
- **2.7.c** Без відповіді `travel_min = NULL` і планувальник рахує `0`: `leave_now` о `due − 15 хв`. Питання без відповіді нічого не блокує й не повторюється.
- **2.7.d** Подія завтра 10:00, `travel=30`, створена сьогодні 12:00 → `eve_before` сьогодні 20:00, `leave_now` завтра 09:15. Створена о 22:00 → `eve_before` немає (питання вже було), `leave_now` є. Створена завтра о 09:50 (`travel_min` NULL) → обидві миті позаду, планувальник нічого не створює (лише `planned_at`); відповідь `tr 30` о 09:51 — це вже 2.7.b: `leave_now` о 09:51 (`fire_at = now`), бо `due_at` ще попереду. Планувальник не створює «минуле», відповідь — створює: правила не конфліктують.
- **2.7.e** Зсув `+15` береться з `LEAVE_BUFFER_MIN`; `travel=60`, `due=10:00` → 08:45. Перехід на літній час (2026-03-29): `due` 10:00 локально → `leave_now` на 30 хв дороги коректний UTC. *Мутант: прибрати «−15» — червоніє.*
- **2.7.f** Тексти `eve_before` і `leave_now` — окремі пули (S2.10); `eve_before` називає час події, `leave_now` — «час виходити» і час початку.
- **2.7.g** Скасований корінь не блокує перепланування: (A) планувальник створив `leave_now` о 09:45 (`NULL`), відповідь «0» → рівно один `pending` `leave_now` о 09:45, без помилки; (B) 30 → 60 → 30 → один `pending` (о 09:15) і два `cancelled`. *Мутант: `ux_rem_root` без `status <> 'cancelled'` — (A) і (B) лишають 0 `pending`, червоніє.*

## Тиша й пауза

### S2.9 · P2 · Режим тиші й одне зведення (крок 2.4)

Режим тиші (`00-common`): `pause_until > now` або локальна хвилина доби в `quiet_from…quiet_to` (`inQuietHours`, є з 1.5). Тихі години не мають винятків, і `important` теж мовчить (виняток для ліків — питання Фази 4).

- **2.9.a** Given `now` у тихі години (23:00–08:00 Київ, 02:00 локально), When cron, Then жодного повідомлення цьому користувачеві; його рядки лишаються `pending`, `attempt` і `fire_at` не змінені; інші користувачі не страждають (множина виключень у `claim`).
- **2.9.b** Тихі години закінчились (08:00): Given рядки з `fire_at` 23:30, 02:00 і 07:59 → на тику 08:00 запізнілих двоє (23:30, 02:00), тож за S2.6 п.1 усе, що зараз у черзі користувача, іде **одним зведенням з трьох** (свіжий 07:59 додається, а не йде пушем слідом). Given єдиний рядок 02:00 → окреме повідомлення без зведення. Given рядки 02:00 і свіжий 08:00 → запізнілий один: обидва окремо.
- **2.9.c** `repeat` у тиші: спроба не витрачається; нащадок створюється лише після реальної відправки (S2.2.a).
- **2.9.d** Переходи на літній час: тиша 23:00–08:00 у ніч на 29.03 і на 25.10 закінчується о 08:00 за місцевим годинником, не за UTC.
- **2.9.e–g** `/pause [N]`, `/resume` і їхня взаємодія з тишею — у зрізі [phase-2-dates-texts.md](phase-2-dates-texts.md) (S2.9, продовження).
